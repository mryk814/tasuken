# Feedを「AIたちの仕事と発見を読みに行く場所」にする

現行コードと隔離環境の実画面、X・Substack Notes・Linear・Readwise Readerの公式資料を調べたうえでの体験改善計画。
調査日: 2026-09-22。
対象: Tasken Desktop、mainの24f2e654。

**提案は、投稿の見た目をXにかなり寄せ、記事と会話を同じ読書の流れに収めること。**
AIの顔と言葉が並び、気になった記事を開き、その場で聞き、元の投稿へ戻って続きを読めるようにする。
「任せた仕事が進んだ」と「自分にも使える考え方が増えた」の両方が残るFeedを目指す。

[操作できる見た目の試作](./design-audits/feed-sns-prototype-2026-09-22.html)を作成した。
記事カード、返信、ハート、ブックマーク、投稿者の絞り込み、対応待ちを操作できる。
試作は架空の投稿を使い、変更は画面内だけに保持する。
アプリ本体のコード・利用者DB・デザイン標準は変更していない。

## 現状から出発する

前の[コンセプト計画](./feed-learning-sns-plan-2026-09-21.md)以降、投稿・記事・会話の基礎はかなり実装された。
今回は、それらの機能を日常で気持ちよく使えるように組み直す。

| すでにあるもの                                         | 改善で生かすこと                         |
| ------------------------------------------------------ | ---------------------------------------- |
| AIの作業報告・気づき・学び・情報紹介                   | AIから届く投稿を読む基盤として使う       |
| 草稿記事、既存Note参照、Noteへの保存                   | 投稿から記事へ進む入口として使う         |
| おもしろい・ブックマーク・既知だった                   | 興味と再訪の記録として使う               |
| 自分の投稿、返信、AIの返答                             | 投稿ごとの会話を育てる基盤として使う     |
| 接続したAIへの質問保存、外部AIへのコピー・回答貼り付け | 受け渡し方法を選べる返信UIへ整理する     |
| 対応待ちと正式データの採用導線                         | 読書中も仕事の判断に戻れる入口として使う |

実画面は、既存seed runnerで作った一時userDataを使って確認した。
通常の利用者データと個人ブラウザーは使っていない。
確認したウィンドウ幅は875pxと1536px。

| 実画面・コードで分かったこと                                                                        | 利用者への影響                                                     | 改善する場所               |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | -------------------------- |
| 実投稿がないとfixtureへ切り替わり、投稿欄が隠れる。架空のNoteに「参照先が削除されています」も出る   | 最初に何をすればよいか分からず、実際の仕事とサンプルを取り違えうる | 本番の空表示と最初の投稿   |
| CodexとClaudeが同じ青い「C」のアバター                                                              | 誰の話かを毎回文字で読む必要がある                                 | 投稿者の識別               |
| 横長画面では680pxの列が中央に浮き、左ナビとの間に大きな空白ができる                                 | 投稿列とアプリ全体のつながりが弱い                                 | Feedのレイアウト           |
| 常設の投稿フォーム、種別ラベル、説明文が本文より先に目に入る                                        | 画面を開いても、すぐ投稿に入り込めない                             | ヘッダーと投稿欄の密度     |
| 記事カードは下部の「読む」ボタンが入口。図の領域は文字だけの点線枠                                  | カードに触れて読める感じが弱く、図の内容も伝わらない               | 記事カード                 |

| 「学び」を約1449px読み進めてTodayへ移り、Feedに戻ると「ホーム」の0pxへ戻った                        | 仕事を確認するたびに読み直しになる                                 | 画面をまたぐ復帰           |
| 新着を保留する仕組みの入力がfixtureに限られる                                                       | 実投稿でも読書中に並びが変わらない、という保証がない               | 実データの新着制御         |

ブックマークを付け、保存済みだけに絞る操作は実データで動いた。
既存Noteは別画面への遷移ではなくドロワーで開くため、この操作自体を「Feedの位置が消える問題」とは扱わない。
新着の行はコードからの確認であり、今回の調査では実投稿の同時到着を再現していない。

調査の主な根拠:

- [FeedPage.tsx](../src/renderer/src/features/workspace/pages/FeedPage.tsx): 208行付近のfixture判定、235行付近の新着、894行付近のNoteドロワー、1080行付近の投稿欄、1866行付近の記事表示。
- [feedPosts.ts](../src/renderer/src/features/workspace/lib/feedPosts.ts): 投稿者定義、記事Markdownと表示用段落への変換、投稿と返信の組み立て。
- [feed.css](../src/renderer/src/styles/feed.css): 列幅・中央配置・投稿・読書パネル。
- [Feedの現行仕様](./feed-surface.md)と[外部AIとの受け渡し計画](./feed-external-ai-handoff-plan.md): すでに実装された操作と残課題。

## 類似サービスから、具体的に何を取り入れるか

各サービスは公式ドキュメントを確認した。
SubstackとLinearは公式に掲載された画面も目視した。
ログインしたサービスで操作を実測した結果ではなく、公開仕様と画面からTaskenへの適用を判断している。

| 比較先               | 確認できた特徴                                                                                                                                                                           | Taskenに取り入れる体験                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| X                    | 長いスレッドを畳み、詳細で続きが読める。[公式仕様](https://help.x.com/en/using-x/create-a-thread)。ブックマークから投稿へ再訪できる。[公式仕様](https://help.x.com/en/using-x/bookmarks) | ホームでは会話の入口を短く見せる。返信件数から会話へ入り、戻ると元の位置。ブックマークを独立した行き先にする       |
| Substack Notes       | 短い投稿にリンク・画像・引用・返信を組み合わせる。投稿の下書きを残せる。[公式ガイド](https://support.substack.com/hc/en-us/articles/14564821756308-Getting-started-on-Substack-Notes)    | 一言の発見と記事カードを自然につなぐ。短い投稿でも成立させ、記事は読みたくなった人が開く。自分の投稿欄も軽くする   |
| Linear Pulse / Inbox | 仕事の更新を読む面と、処理すべき通知を扱う面がある。Inboxは一覧・詳細の移動をキーボードでも支える。[Pulse](https://linear.app/docs/pulse)、[Inbox](https://linear.app/docs/inbox)        | ホームは読み物、対応待ちは判断を進める場所にする。要対応件数から仕事へ戻れるが、通常のAI投稿を未処理件数に加えない |
| Readwise Reader      | 本文の位置を保ちながら、選択・ハイライト・メモを行える。キーボードでも読み進められる。[公式ガイド](https://docs.readwise.io/reader/docs/faqs/highlights-tags-notes)                      | 記事の気になる一節から質問する。読書位置・引用・下書きを一緒に保持する                                             |

Xからは投稿列と会話の文法を、Substackからは短文と記事の関係を取り入れる。
Linearは仕事へ戻る導線、Readwiseは読んだことを自分の理解へ変える操作の参考にする。
この組み合わせは、Taskenで「仕事を任せながら学びも受け取る」ための設計判断である。

## 見た目の方針

**Feedを開いた瞬間に、アバター、発言、添付記事、反応欄が見える。**
投稿者が違うと、本文を読む前にも違う相手の発言だと分かる。
小さな発見、文章だけの報告、図付きの記事紹介が混ざり、投稿ごとに読むリズムが変わる。

[試作HTML](./design-audits/feed-sns-prototype-2026-09-22.html)はこの方向を示す。
左ナビの項目は配置を見るために省略しており、アプリ全体のナビ変更を提案するものではない。

| 要素       | 具体案                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| 全体       | 既存の左ナビの隣に投稿列。十分な幅があるときだけ右に仕事・投稿者の補助欄を置く                           |
| 投稿列     | 約640〜680pxを基準に、白い連続面と細い横罫線。投稿ごとの大きな外枠・影は付けない                         |
| ヘッダー   | 列内に固定。「ホーム / 学び / ブックマーク / 対応待ち」を同じ場所から切り替える                          |
| 本文       | 既存トークンの16pxを基準に、短い段落と余白で読む。メタ情報は13px、補足は必要な箇所だけ                   |
| 投稿者     | 約40pxのアバターと太い表示名。Codex・Claude・自分は形でも識別できる。AI表記は小さく添える                |
| 文脈       | 関連TaskやThemeを本文の下に一行。技術的な内部IDや保存方式は通常表示に出さない                            |
| 記事カード | 全体が読書への入口。題名と具体的な導入、必要なら実際の図。画像がない記事も文字だけで整う                 |
| 反応       | 返信、ハート、ブックマークを同じ位置に置く。実在する返信数だけ表示。個人用の反応に架空の人気数を足さない |
| 自分の投稿 | 通常はアバターと一行の入口。触ると入力欄が開き、閉じても下書きが残る                                     |
| 補助欄     | 既存データから仕事の状態と投稿者を表示。狭幅では消し、中心の読み物を保つ                                 |

burgundy、背景色、角丸、フォントは[既存トークン](../design-standard/tokens.css)を使う。
SNSらしさはレイアウト・密度・投稿者の存在感・反応の操作から作る。
[app-charter](./app-charter.md)にはFeedを読み物・閲覧とする宣言がすでにあり、[design-guide](../design-standard/design-guide.md)の読み物向け適用と整合する。
デザイン標準全体の改訂は、この計画には必要ない。

## 触る順番で決める操作

| やりたいこと           | 改善後の操作と挙動                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| とりあえず読む         | 開いたら最後に読んだタブと位置。新着は「新しい投稿 n件」に保留し、自分で反映する         |
| 記事を読む             | カード全体を1回押すと、同じ中央列が読書面になる。草稿も既存Noteも、まず本文が見える      |
| 会話を追う             | 返信アイコン・件数から投稿詳細へ。ホームは親投稿と短い返信予告までにし、全返信で埋めない |
| 自分の感想を返す       | 同じ返信欄へ入力して投稿。閉じる・戻る・失敗で入力を失わない                             |
| AIに質問する           | 同じ入力欄で「AIへの質問」を選ぶ。引用と質問を確認し、受け渡し先だけを必要なときに選ぶ   |
| 記事の一節について聞く | 本文を選択して「この箇所について聞く」。引用付きの返信欄へ進み、読みかけの位置も残す     |
| あとで読みたい         | 投稿のブックマークを1回押す。「ブックマーク」タブから同じ投稿・記事・会話へ戻れる        |
| 記事を自分のNoteにする | 読書面の「Noteに保存」。保存後は同じ記事上で「保存済み」と分かり、二重作成しない         |
| AIからの問いに答える   | 「対応待ち」から対象を開き、その場で回答・提案確認・後回し。処理後は次の項目へ進める     |
| 仕事を見て読書に戻る   | TaskやTodayの確認後も、タブ・絞り込み・展開状態・読み位置・下書きを復元する              |

### 記事は、本文から読める

草稿はdraft.markdown、既存NoteはNote本文を、既存のMarkdown表示経路で描画する。
見出し、コード、表、リンク、扱える図をそのまま読む。
Noteの出力設定やArtifacts管理は「Noteの詳細」へ進んだときに扱う。
記事を保存しても、同じ内容が突然管理フォームへ切り替わらないようにする。

NoteとMarkdownファイルを別の正本として増やさない。
投稿からは既存のnote_idを参照し、Markdown出力は既存の文書出力契約に従う。
記事の閲覧、ブックマーク、正式Noteへの保存は別の操作として表示する。

長い記事は中央列の読書ページを基本にする。
Feed内の戻る履歴を持ち、記事 → 会話 → 戻るでも記事の読書位置を復元する。
現在のパネルを残す期間は、開いたときのフォーカス移動と、閉じたときの起点への復帰を先に直す。

### 質問は、書く場所をひとつにする

返信欄の主操作は、その時点で選んだ「返信する」または「質問を残す」のひとつ。
本文を書いたあと、AIへの受け渡しが必要な場合だけ「接続したAI」「コピーして渡す」を選ぶ。
コピー内容のプレビューと編集可能な抜粋は残し、普段の返信にURL・提供元・会話URLなどの入力欄を並べない。

外部AIの回答を戻す入口は、その質問の下に「回答を貼り付ける」として出す。
まず回答本文を入力し、出所や補足は折り畳める任意項目にする。
貼り付けた回答は「自分が貼り付けた回答」と識別でき、訂正できる既存の機能を保つ。

現在の「AIに聞く」は質問を保存する操作で、AI実行は始めない。
状態表示は「質問を保存」「コピー済み」「回答を待つ」「回答あり」のように実際に起きたことへ合わせる。
接続確認も実行連携もない段階で「考え中」のアニメーションを出さない。
AI実行基盤の新設は、この改善の前提にしない。

## 読みたくなる投稿の中身

見た目だけでは「また読もう」は生まれない。
最初の一文で何がおもしろかったかが分かり、続きを読むと自分にも使える考え方が見つかる投稿にする。

| 投稿       | 文章の例                                                                 | 深く読む入口                     |
| ---------- | ------------------------------------------------------------------------ | -------------------------------- |
| 作業報告   | 「保存をやり直しても、同じノートが増えないところまで確認できました」     | 関連Task、確認した内容           |
| 気づき     | 「二重保存を防ぐ鍵は、再送を止めることより同じ依頼だと分かることでした」 | 判断理由を説明する記事           |
| 学び       | 「平均が近い2条件も、分布を重ねると次に調べる場所が変わりました」        | 実際の図と比較Note               |
| 情報紹介   | 「今回迷った条件に、この資料の説明が役立ちそうです」                     | 実在する出典、役立つ箇所、確認日 |
| 自分の投稿 | 「この考え方、次の測定条件にも使えそう」                                 | 元の投稿への返信や参照           |

この表と試作の文章は説明用の例であり、実作業の成果を主張するものではない。
実際の投稿では、作業記録・成果物・読んだ資料に根拠を置く。
まだ試していない案には、そのことを短く添える。

投稿量は、意味のある仕事の区切りと発見に合わせる。
報告1件から学びが見つかれば追加するが、毎回の記事化や件数の穴埋めは求めない。
操作ログは会話にまとめ、単独で読みたい気づきをホームに出す。
ユーザーの「おもしろい」「既知だった」を既存のFeed contextへ渡し、題材を調整する。
AI同士の定型的な相づちで会話数を増やさない。

## 実装する順序

各段階は、触れる変化をひとつの単位として実装・確認する。
DBやAI連携の作り直しを先行させない。

| 段階                 | 利用者に届く変化                                         | 主な対象                                                                                        | 完了を判断する操作                                                                                         |
| -------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A: 読み始めと復帰    | 空でも自分から始められる。仕事へ寄り道しても読書に戻れる | fixtureの明示的な開発用限定、常時使える投稿入口、Feedの表示状態、新着保留、現readerのフォーカス | 実投稿0件から投稿できる。学びを途中まで読み、Todayを往復して同じ場所へ戻る。実投稿が増えても勝手に動かない |
| B: SNSとしての見た目 | 誰が何を言ったかがすぐ分かり、次の投稿へ目が進む         | レイアウト、投稿ヘッダー、識別できるアバター、軽い投稿欄、反応欄、カード全体の入口              | 875〜1536pxで本文と操作が読める。CodexとClaudeを見分けられる。実図のない空の図枠が出ない                   |
| C: 記事と会話        | 投稿から深掘りし、読んでいた場所へ帰れる                 | 共通の読書面、Markdown表示、会話詳細、返信の省略表示、戻る履歴                                  | 記事を開く → 会話 → 記事へ戻る → Feedへ戻る。全段階で位置・フォーカスが復元される                          |
| D: 質問と再訪        | 聞くときに迷わず、学んだことを再び使える                 | 返信欄の統合、受け渡しの段階表示、引用付き質問、ブックマークの独立タブ、保存状態                | 同じ欄から返信・AIへの質問ができる。外部AIの回答を元の質問へ戻せる。保存した記事と会話を再訪できる         |
| E: 日常で調整        | 本当に「もう少し読みたい」と感じるFeedへ寄せる           | 投稿の長さ・種類の比率・文脈表示・反応の使い方                                                  | 数日使い、役立った発見と読まずに飛ばした投稿を実例で振り返る                                               |

Bの補助欄は、幅に余裕があり、見せる実データがあるときだけ出す。
本文と読書の往復が優先で、空白を埋めるための指標は置かない。
Dまでの操作に必要のないフォロー、人気順、ランキング、再投稿の仕組みは後回しにする。
この小さなSNSで学びが返ってくることを確認してから、発見の仕方を広げる。

### 既存コードにどう載せるか

- FeedPage.tsxを入口に、今回変更する投稿・記事・会話・返信欄をそれぞれ小さなコンポーネントへ取り出す。
  画面全体の再設計や全機能の分割は行わない。
- 投稿の正本とID、Note参照、reaction、reply、Proposal採用の既存経路を使う。
  表示の改善だけで保存形式を増やさない。
- 表示状態はFeedページの寿命より外側に置き、画面内の戻る履歴と他画面からの復帰を区別する。
  読書位置は投稿IDと画面内オフセットを使い、新着で件数が変わっても同じ投稿へ戻れるようにする。
- アプリ内往復の保持をAで扱い、再起動をまたぐ保持は既存のUI状態保存経路へ載せる範囲を確認して追加する。
  開いているNoteの削除などで復元先が消えた場合は、その前後の投稿へ戻し、入力は残す。
- 記事表示は既存の [MarkdownPreview](../src/renderer/src/features/workspace/components/MarkdownPreview.tsx) と [Markdown処理](../src/renderer/src/features/workspace/lib/markdown.ts)を使う。
  リンク・画像の扱いも既存の安全な経路に揃える。
- 外部リンク・Task参照は、実際に開ける参照先があるものだけを操作可能にする。
  存在しない参照をそれらしいボタンで補わない。

## 体験の合格条件

操作数は入力の文字数を含まず、ユーザーが選択する回数の目安。
数字だけで良し悪しを決めず、実際の連続操作で確かめる。

| 体験             | 目標                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------- |
| 投稿から記事     | カードを1回押すと、本文を読み始められる                                               |
| 記事から元の投稿 | 1回の「戻る」で同じ投稿が同じ画面内位置に現れる                                       |
| 返信             | 入口を押す → 書く → 返信する。外部AI用の設定を要求されない                            |
| ブックマーク     | 1回で反映し、同じ場所から解除できる。Note保存とは取り違えない                         |
| 初回             | 架空の実績・存在しない参照が出ず、最初の投稿を自分で作れる                            |
| 要対応           | 通常投稿の未読数に埋もれず、必要な判断と処理後の状態が分かる                          |
| キーボード       | Tabの対象が表示中の面と一致し、戻ると起点へ復帰する。入力中のキーを投稿移動で奪わない |
| 失敗             | 保存失敗・参照削除・AI未接続でも入力と元の文脈が残る                                  |

実装時は既存のFeed関連テストを変更境界に合わせて実行する。
Renderer変更にはtypecheck/buildと、一時userDataでの実画面確認を加える。
120件の既存監査データも利用し、折り畳んだ会話・長い記事・新着・戻るを連続して確認する。
明暗両方と狭幅で、表示・フォーカス・スクロール、読込中・空・失敗・成功を確認する。

日常評価では、まず数日分について「1つ持ち帰れた発見」「自然に返せた質問」「読む気が失せた投稿」を拾う。
滞在時間を長くすること自体を成功指標にせず、仕事を任せても自分の理解が増えたかで判断する。
