# Feedを使った感想（2026-09-22、利用者の実機操作）

利用者が、マージ済みmain（`24f2e654`）のデスクトップアプリを実際に触ったときの口頭フィードバック。
対象は主にFeedの投稿・返信・反応。
[Feed UX改善計画](./feed-ux-improvement-plan-2026-09-22.md)と[試作](./design-audits/feed-sns-prototype-2026-09-22.html)を踏まえてUI・体験を進める際の入力にする。

記録の性格: 利用者の言葉を要約したもので、実測値ではない。件数・割合は測っていない。
「良かった」は感想であり、検証の完了を意味しない。

## 良かった点

- 素朴に動く。「もうできとるやん」という感触で、キットとしてかなり良い
- 投稿の内容そのものが興味深い。アイコンや見た目が洗練されれば十分という水準
- 普段使うAIへ貼り付ける仕組みは、思ったより必要な仕組みだと感じた
- 投稿の返信から触り始めて、全体的に興味深いという評価

## 改善したい点

### 1. 反応（いいね・ブックマーク・返信）をアイコンにする

現在の反応欄は文字が主体で、想定と違う。いいね・ブックマーク・返信には既定のアイコンがあるため、それを使って分かりやすくする。

### 2. 投稿の種類をもっと分かりやすくする

種別（気づき・情報紹介・質問など）は今も文字で出しているが、**何の種類なのかが一目で分かる**ようにする。種類の識別は優先度が高い。

### 3. 投稿者（サービス）の識別性を上げる

**アイコンで識別できるようにする。** 完全に個人用のアプリなので、各サービスのアイコンを気楽に使ってよい。分かりやすさを優先する。

利用者が挙げた対象:

- Claude Code
- Codex
- GitHub Copilot
- Cursor
- DeepSeek
- Gemini
- Antigravity
- OpenCode

実装方法（アイコンの入手・使い方）は難しいかもしれないという前提で、**識別性を上げること自体を目的**にする。

補足（実装時に決めること）:

- [design-guide](../design-standard/design-guide.md) §3 はUIアイコンの正本をTabler Iconsとし、同一アプリ内でアイコンセットを混ぜないとしている。
  サービスロゴはUIアイコンではなく**アバター（出所の識別）**の一種として扱い、用途を分けて計画に明記する。
- ロゴは各サービスのブランド資産である。個人利用の範囲で使う判断は利用者がしており、ライセンス確認は実装時の確認項目にする。
- 提供元の公式アセットが無い場合は、頭文字と色で区別する現行方式へフォールバックする（架空のロゴを作らない）。

### 4. アイコンで足りるものを文字で表現している

反応欄・種別・補足など、**アイコンで成立する情報を文字で多く書いている**点が気になる。
これは修正してよい（利用者も「直せばいい」としている）。

### 5. 画面をまたぐ復帰（戻る概念）は別課題

> 「原点を開くまでちょっと動き、なんかどっかに飛んじゃうと戻ってこれない。タスケン元々のタスケン内での移動をあんまり考慮できてない。戻るとか何かしらの概念があんまりないから、どっかに飛んじゃうと行きっぱなしみたいな雰囲気がある」

利用者自身が「そこはそことして」と切り分けているが、**Feed固有ではなくアプリ全体の移動の問題**として記録する。
Feedから元の投稿・記事・Task・Todayへ移った後の帰り道が保証されていない。

### 6. 経路の位置づけ: MCPが本線、貼り付けは特殊ケースの補助

**この節は記録中に2度訂正した。最終的な利用者の判断は次。**

**MCPへ接続してTaskenへ情報を入れてもらうことを圧倒的に推奨する。なるべく全武装したい。**

- Codex、Claude、Cursor、GitHub Copilot、Gemini、DeepSeek、Antigravity、OpenCode など、MCPへ接続できるAIには接続してもらい、投稿・記事・回答・作業報告をTaskenへ入れてもらうのが**本線**
- したがって改善の主対象は「**MCPで入れられる情報を増やす・楽にする**」側にある
- 既存の `tasken.propose_feed_post`、`tasken.answer_feed_question`、`tasken.get_feed_context` などの経路を育てる方向

**M365 CopilotのようなMCP接続できないパターンがむしろ特殊。**

- その特殊ケースの補助として、人間がproxyとなってコピーと貼り付けで往復する経路がある
- 補助ではあるが、**使う場面では楽であるべき**。コピーと貼り付けの手数、任意項目（出所・会話URL・自分の一言）の負担、往復の途中で迷わないことを下げる
- 「普段使うAIに貼り付ける仕組みは思ったより必要だった」という評価は、この特殊ケースの重要性を指している

**記録の経緯（同じ誤りを繰り返さないため）**

1. 当初「MCP接続済みが本線、クリップボードは非MCP向け」と書いた
2. 「M365のMCP接続は難しいので、人間proxyの貼り付けが本線」と訂正した（振りすぎ）
3. 最終: **MCPが本線で全武装したい。MCP接続できない場合が特殊で、その補助が貼り付け**
