# Taskenの設計・データ契約

機能境界、保存契約、Import/Export、AI連携、ログを変更するときに該当節を読む。
既存データと実装を起点に必要な変更へ適用する。既存機能の一括作り直しや、未使用のschema・依存追加を求めるものではない。
検証の範囲と完了条件は [AGENTS.mdのTesting](../AGENTS.md#testing) を優先する。

## Application architecture principles

- 利用者の入口から保存・再表示・編集・削除/復元まで一つの経路を通す。新機能は既存導線への統合を先に検討する。
- 正式データの正本を一つにし、派生表示・一時入力・UI状態を分ける。一覧・詳細・Exportは同じ正本から作る。
- Resource編集の「元チャット」候補はResourceと旧Linkをidで一件にまとめ、同じidのResourceを優先する。旧Linkだけの候補は保持する。
- 保存APIの成功後に正式stateを更新する。失敗時は入力と既存データを保持し、再試行や復旧の導線を示す。
- UI、業務処理、永続化、OS操作の責任を分け、entry pointは接続と起動に限定する。外部入力は境界で検証し、内部では型付けした業務語彙を使う。
- 共有する正式データ・非同期状態はstoreへ、画面内の途中入力や開閉はcomponentへ置く。派生値はselector/純粋関数に集約する。
- モジュール分割は変更理由・責任・再利用の必要性で判断する。ファイル行数を理由に分割せず、未使用の層・interface・設定を先回りして追加しない。
- 依存は対象checkoutの環境で管理する。他パッケージの`node_modules`を`file:` symlinkで参照しない。
- 複数の正式データを同時に変える操作はtransaction等で完結させる。汎用の「何でも実行できるAPI」を公開しない。
- 新しい保存経路は型・契約→永続化→業務処理→API→state→UIを縦に接続する。成立後に旧経路を撤去し、同じ責任を二重に残さない。
- 大きな移行は既存データ、Import/Export形式、API、主要操作、配布結果の互換条件を先に固定する。段階ごとに変更の影響を受ける条件を検証し、ビルド・起動可能な状態へ戻す。
- 文書には現在の正本、互換条件、未完了事項を残す。完了した旧entryや移行TODOは撤去し、意図的に見送る機能には導入条件を記録する。

Note編集はTheme変更も含めてDocument保存へ通す。本文由来のReferenceと、そのNoteを参照する未削除のNote/Report ArtifactのThemeは同じDB transactionで更新する。外部Markdownの書き込み失敗は既存の同期状態と再試行で扱い、DBとファイルの同時commitとはみなさない。

## データモデルと永続化の標準

プラットフォームに依存しないデータ設計の規約。SQLite・JSONファイル・localStorageのいずれでも従う。

**適用範囲**: この章の対象は「アプリが正本データを所有する」場合（蓄積・編集・再表示するデータをDB/JSONに持つアプリ）。ファイルが正本でアプリは加工するだけのツール（変換・結合等）や、外部ソースの読み取り・可視化のみのツールは、入出力の検証・プレビュー（12項）とExport往復性（17項）だけ守ればよい。どちらに当たるかは `docs/app-charter.md` の「データの重さ」で宣言する。

1. エンティティは共通カラムを持つ: `id`（UUID。連番IDは使わない）／ `created_at` ／ `updated_at` ／ `deleted_at` ／ `version`（保存するたびに+1する。取り込み時に新旧を判定する基準にする）／ `source`（"manual" | "imported" | "quick-capture" 等、データの由来を示す文字列）。
2. 日時は ISO 8601 形式で保存する。日付のみのフィールドは `YYYY-MM-DD` 形式にする。ローカル日付文字列を `toISOString().slice(0, 10)` で作らない（UTCとのずれで日付がずれる）。`getFullYear` / `getMonth` / `getDate` から組み立てる共通ヘルパー関数を1つ用意し、日付文字列の生成箇所すべてでそれを使う。
3. 削除は論理削除（`deleted_at` にタイムスタンプを入れる）を既定にする。物理削除は明示的な要件がある場合だけ行う。削除は、完了・受領・却下・アーカイブなどの状態変更とは別の操作として設計する（同じボタン・同じ関数で兼用しない）。
4. 関連エンティティが削除された場合の扱いは、型ごとに列挙した delete policy 関数1箇所にまとめる。参照は nullify（切り離す前の参照値を退避フィールドへ記録する）、子は cascade（削除元を示すマーカー付きで論理削除する）のいずれかにする。restore 操作は、退避した参照値とマーカーから元の関連を完全に復元できることを条件にする。新規エンティティを追加するときは、この delete policy 関数への追記を必須の作業項目にする。
5. enum に相当する値は文字列 union（`as const`）で定義する。DBに保存する値は英語 snake_case にし、画面に表示するラベルは対応表1ファイル（例: `labels.ts`）に集約する。UIコード内に表示文言を直書きしない。enum フィールドを1つ追加したら、同じ変更の中でラベル対応表にも追記する（内部コードがそのまま画面に表示される事故を防ぐ）。
6. ユーザーが並べ替える対象にだけ `sort_order`（数値）カラムを持たせる。配列に格納されている順序に暗黙で依存しない。Taskのカンバン列内順序は用途を明示した任意の `board_order`（0以上の安全な整数）として正本Entityへ保存し、再起動・Import/Export・同期で保持する。未設定の旧Taskは手動順序のあるTaskの後ろに、作成日時・IDの安定順で表示する。状態移動と順序更新は同じtransactionで保存する。
7. migrationは「スキーマのバージョン番号」と「連番のmigrations配列」で管理する。適用済みのmigrationは内容を書き換えない。DBのバージョン番号がアプリのバージョン番号より新しい場合はアプリの起動を拒否する。
8. 参照整合性とデータの循環参照は、DBのFK制約に任せず、保存時にアプリ層で検証する。存在チェック（参照先が存在するか）と循環チェック（親子・依存グラフの中で閉路が生じないか）の両方を行う。
9. DBのrow型とアプリのDomain型は別の型として定義し、永続化層（Repository相当）で変換する。
10. 「作成→一覧→詳細→編集・削除→永続化」という利用者が到達できる一連の操作（成立ループ）が通らないテーブル・カラムを先に作らない。「将来使うかもしれない」構想はバックログに文章で書き、schemaには反映しない。
11. データモデルの世代交代では、移行期間中は旧形式と新形式の両方を読めるようにする。旧形式を参照するフィールド・テーブルは `legacy_*` という命名で識別できるようにする。
12. Import（表やファイルからの取り込み）は必ず次の順で行う: 検証 → プレビュー（既存データとのdiffを新規・同一・更新・衝突に分類して提示） → ユーザーが採用/上書き/無視を決定 → 適用。検証やプレビューを経ない無条件の直接上書きをしない。NotesへのMarkdownファイルのドロップは、利用者の操作で新規Noteだけを作る経路とし、既存データを上書きしない。
13. 一覧のフィルタ条件が複数の独立したフィールド（例: 状態×種別）の組み合わせで決まる場合、片方のフィールドだけを変更した結果「保存されてはいるが、どの一覧にも表示されない」データが生まれないかを設計時に確認する。
14. 変更履歴（何が・いつ・なぜ変わったか）は、意思決定の再現と失敗時の復旧に必要な箇所へ設計に含める。
15. **自動バックアップ**: ローカルファーストのアプリは、起動時または終了時に自動でバックアップ（Taskenでは正本データベースの写し）を書き出し、確かめてからN世代（既定5）をローテーション保持する。手動Exportだけに頼らない。保存先と世代数は設定画面に出す。戻す操作も設定画面に置き、戻す前に今のデータを自動で控え、戻した後に件数を確かめる。失敗したときは戻す前のデータのまま起動する。
16. **書き込み経路の一本化**: 複数のウィンドウ・プロセスから同じデータを扱う場合、書き込みは単一の経路（例: Main Process の Repository）に集約し、変更通知で他のウィンドウへ反映する。各ウィンドウが直接ファイル・DBへ書かない。
17. **Exportの往復性**: ExportしたデータをImportし直したとき同じ状態に戻ることを、Export/Import機能の検証項目に含める。

新規エンティティでは、一覧・詳細・編集・Undoそれぞれの削除/復元導線を確定し、delete policyとラベル対応表を更新する。
既存の形式変更には必要な移行または互換読み取りを用意し、利用実態を確認せずUIの削除をデータ廃止と同一視しない。

## AI連携の標準

アプリとLLMを連携させる場合の既定方式。

1. LLM APIをアプリに内蔵しない構成を既定にする。標準の連携方式は**クリップボード往復**にする: プロンプト文字列を生成する → クリップボードへコピーする → 利用者が外部AIへ貼り付ける → 返答（JSON等）をアプリへ貼り戻す → パースする → プレビューを表示し採用/無視を選択させる → 保存する。
2. MCP等でAIにアプリへ直接アクセスさせる場合は read-only を既定にする。書き込みを許可する場合は「提案（proposal）エンティティを作成するだけ」を既定にする。提案を実データへ反映するのは、利用者がUI上で内容を確認し採用を選んだ後にする。本人が許した新規作成専用経路は例外としてTask/Noteを直接保存できる（Desktopは設定で許し、Theme・日程・優先度・チェックリスト・今日の割当も受ける。NASはcreate-only配備で許し、同じ欄を受ける）。保存済みであることと既読・情報の正確さの確認を分離し、AI由来を保持する。既存データの編集・削除・完了・委任には適用しない。
3. AIからの取り込みも、上記「データモデルと永続化の標準」の Import と同じ「検証→プレビュー→決定→適用」の手順に従う。取り込みが失敗した場合、既存データと入力途中の値の両方を保持したままにする。
4. 人がProposalを採用して**新しくEntityが作られた**とき、そのEntityへ`accepted_from_proposal_id`（Proposal ID）を保存する。既存Entityの更新では上書きしない（最初に作ったProposalを失わないため）。`source_type`/`source_id`はActivityの参照へ波及するため、この用途には使わない。
5. 外部AIは`tasken.get_proposal_status`で受領IDから採否と作成Entityを確認できる。応答は**接続中のnodeが持つ正本**だけを表し、別端末への配送とそちらでの採否は確認しない。未採用のProposalにはEntityを返さない。`tasken.list_proposals`は同じnodeのProposalを識別と状態だけで一覧し、payload本文は返さない。
6. Proposal・読み物の書き込みで`dry_run: true`を指定した場合、Coreは本送信と同じ検証だけを行い、Proposalの保存・画像のstage・Feedへの表示をしない。応答は`status: "validated"`とし、保存されていないことを明示する。

Desktopのローカル接続（stdio）では、本人が設定で直接の書き込みを許したとき、既存Taskの直接変更（`task.ai_change`）も受ける。入口はCoreの限定の`/v1/commands/change-task`・`/v1/commands/undo-change`だけで、actor（ai_agent）とsource（mcp）はCoreが固定する。変えてよい欄は許可リスト（題名・本文・Theme・優先度・日程・今日・棚・開始時刻と所要・リマインダー・場所のリマインダー（座標は本人が言った場所か確かな出典からだけ。推測しない）・チェックリスト）に限り（AIへの新しい委任`intended_executor=ai_agent`と依頼の文は`DELEGATION_RETIRED`で断る。前の版で委任したTaskを`self`へ戻すのは受ける。#755 束10a）、完了・再開・削除（tombstone）は操作で分ける。必ず`expected_version`を照合し、違えば409で今のTaskを返す。本人の言葉（`said`）が要る変更を`why`だけで送ると保存せず`ASK_USER`（422）を返す。要らないのは、AIが作って本人がまだ一度も触っていないTaskと、`why`で決めた変更の取り消しだけ。委任した作業の最中・繰り返しの完了・同期の競合中のTaskは断る。一つの会話（`source_session`）で30件を超えるTaskを変えようとしたら`ASK_USER`で止め、本人の言葉と`confirm_bulk`で次の30件。根拠・会話・要求の指紋は全Change Eventの`metadata.ai_direct`に残す。取り消しは、変えたTaskがその変更の直後の版のままなら前の値へ戻す新しいcommandで、削除は連鎖した子ごと復元し、後から別の変更が入っていれば止める。本人の言葉で決めた変更の取り消しには本人の言葉が要る。直接の変更はFeedに流さない。存在しない（削除済みを含む）Taskは`NOT_FOUND`、無いThemeへの移動は`INVALID_REFERENCE`にする（再送とAIの取り消しも同じ）。AIに見せる・見せないの区別は無い。会話（`source_session`）は呼び出し元（`source_app`）と組で数え、別のAIのまとめての取り消しに混ざらない。私用のWorkspaceのNAS replicaは、`create-only`の配備に`--allow-ai-task-change`を足し、HTTPのクライアントに`allowTaskChange`を書いたときだけ同じ入口を出す。取り込みが遅れている間は`REPLICA_BEHIND`で断る。

Taskの時刻と期限の知らせは、Desktopとスマホが同じ決まりで、それぞれ端末の中で出す（決まりの正本は`src/shared/taskNotifications.ts`と、同じ内容の`android-app`の`TaskNotificationPlan.kt`）。時刻を付けたTask（`reminder_at`）はその時刻に知らせ、逃した時刻は24時間まで後から出す。期限の日（日程の終了日、無ければ開始日）は、本人が端末ごとに決めた時刻（既定09:00、2回目を足せる）に、その日のうちだけ知らせる。完了・中止・削除したTaskは知らせない。期限の日の時刻は端末ごとの設定で、同期しない（Desktopは`workspace_meta`、スマホは端末の設定）。`reminder_at`は、時差つき（その瞬間）か、Desktopの画面が書く時差なしの現地時刻（`YYYY-MM-DDTHH:mm`。開いた端末の現地の時刻として読む）。AIの`create_task`・`change_task`は時差つきだけを受ける。Mobile Gatewayは要求に`X-Tasken-Reminder-At: 1`があるときだけTaskの要約に`reminderAt`（保存された値のまま。無ければnull）を載せる。通知の「後で」は、UpdateTaskの`changes`/`base`に`{ reminderAt: "..." | null }`を単独で送る。schemaの版は上げない。

Taskの場所のリマインダー（`place_reminder`）は、地名・座標・半径（100〜2000m、既定300m）・曜日・時間帯（日またぎ可）をTaskが正本として持ち、スマホがその場所に居続けたときに通知する条件にする（Desktopのドロワーの「場所」、AIの`change_task`、Androidの更新で付け外しできる）。Mobile Gatewayは要求に`X-Tasken-Place-Reminder: 1`があるときだけTaskの要約に`placeReminder`（camelCase。無ければnull）を載せる。古いAPKは未知の欄で落ちるため、ヘッダの無い要求には欄ごと出さない。schemaの版は上げない。更新はUpdateTaskの`changes`/`base`に`{ placeReminder: {...} | null }`を単独で送る。時間帯は`time_from`と`time_to`が同じ値ならその1分だけ、`time_from`が`time_to`より後なら日またぎ（Androidの判定と同じ）。保存・同期の取り込みでは「nullか普通のobjectか」しか見ず、範囲・昇順・時間帯の組はコマンド入力のschemaが断る（先の版が範囲を広げても同期が止まらないように）。読み出しは既知のキーだけに絞って検査し、読めない値は無い（null）として返す（DBの生の値は変えず、他の欄の更新でも残る）。

続けることの実施記録（`habit_entry`）は、任意の欄`source_command_id`（文字列1〜200文字）を持てる。スマホが`/v1/routine-actions`へ`mode: "append"`（1回足す）で送った記録の commandId で、同じ commandId の送り直しを増やさず、圏外の間にPCが同じ日に記録していても次の空いた回に入れて端末の1回を黙って落とさないために残す。`mode`の無い古いAPKの形は送られた回に保存し、この欄を付けない。`mode: "append"`の受領にだけ、保存後のそのHabitの数（記録の日の`todayCount`・`weekCount`・`nextSequence`）を任意の`habit`で返し、スマホは端末の写しをその値で上書きする（古いAPKは受領の知らない欄で落ちるので付けない）。既にある記録には無いまま（移行なし）で、知らない版は欄を検べずに残す。

Desktopの同じ接続で、Noteの直接編集（`/v1/commands/edit-note`）とProposalの採否（`/v1/commands/decide-proposal`）も受ける（`ai_direct_write`。取り消せないのでNASには出さない）。Noteの編集は「Note編集のProposalを作り、その場で採用する」で、版（`base_version`）の照合とCanonical Markdownの保存はDesktopの採用と同じ経路を通る。本人の言葉の要否はTaskと同じ（AIが作って本人がまだ触っていないNoteだけ要らない）で、断るときはProposalを残さない。採否は本人の言葉（`said`）が必ず要り、作業報告（task_work）とNote（作成・編集の一件）だけを扱う。作業報告の採用ではTaskも完了にするかを`complete_task`で明示する。ほかの種類は`DECIDE_IN_DESKTOP`で断り、本人の画面に任せる。人の確認に限っていた作業報告の採用は、本人の言葉を取り次ぐこの入口だけを例外にする（actorはai_agentのまま、根拠を記録する）。

AI Readyの開始（`task.start_work`・MCPの`start_task_work`）は #755 束10a で外した。AIがTaskを動かす道は、本人が設定で許した直接の書き込み（`change_task`など、本人の言葉を根拠にし、取り消せる）だけ。汎用の`task.command`はloopbackに出さない（actorを呼び出し側が書くため）。前の版で記録した開始の来歴（change_event）と作業報告（work_receipt）はそのまま読める。

Coreの全権tokenはdiscoveryで共有するMCP bridge用に限る。MCPを経由しないローカルの読み取りクライアントには、名前つきの読み取り専用tokenを発行する。保存はSHA-256だけで、取り消しは即時に効く。読み取り専用tokenはquery routeだけを通し、Proposal状態・Proposal作成・書き込みを拒否する。接続先はtokenを含まないendpoint fileで公開する。詳細は[外部AI連携](external-ai-integration.md#読み取り専用のローカルクライアント)。

NASのStreamable HTTP MCPは`127.0.0.1`の`/mcp`だけで受け、Tailscale Serveのtailnet内HTTPSから接続する。Core discoveryの全権tokenを外部クライアントへ配らず、bridge専用のクライアント別Bearer tokenを使う。tokenなし・不一致は401とし、クライアントの`readOnly`は既定true、`TASKEN_MCP_READ_ONLY=1`を越えて書き込みを許可しない。HTTP側は汎用編集・削除・完了を公開せず、明示されたCoreの`proposals` / `create-only`の範囲を上限にする。stdioとHTTPは同じCoreを使い、HTTPがSQLiteを直接開く経路を作らない。配備とtoken管理は[Synology手順](synology-headless-node.md#tailnet内のstreamable-http-mcp673)に従う。

## セキュリティと秘密情報

1. 秘密情報（APIキー・トークン・パスワード）をソースコード・設定ファイルに直書きしない。リポジトリにコミットしない。
2. 秘密情報は環境変数または `.env`（必ず `.gitignore` に登録）へ置く。リポジトリには値を空にした `.env.example`（キー一覧）を置く。
3. Electronで利用者の資格情報を保存する場合は `safeStorage` で暗号化する。平文のJSON・localStorageに書かない。
4. ログ・エラーメッセージ・Export・クリップボードコピーに秘密情報を含めない。
5. テレメトリ・クラッシュレポート等の外部送信は既定で入れない。

## エラーハンドリングとログ

1. エラーを握りつぶさない。`catch` して何もしない場合は、無視してよい理由をコメントで書く（例: 効果音の再生失敗は機能に影響しない）。
2. 想定内の失敗（検証エラー・ユーザーによるキャンセル）と想定外の失敗（例外）を区別し、想定外だけを error として扱う。
3. UIに出すエラーは原因＋直し方（design-guide §7）。ログに残すエラーは発生箇所・原因・スタックを含める。両者は役割が違うので同じ文字列を使い回さない。
4. デスクトップアプリは Main 側で userData 配下にファイルログを書く。レベルは info / warn / error の3段にする。
5. ログに秘密情報とデータ本文を書かない。エンティティはIDと件数で書く。
6. 入口ごとの計測は userData の `request-stats.sqlite`（本体の DB とは別ファイル）に持つ。残すのは入口の名前（HTTP は `<METHOD> <ルートの型>`、MCP は `POST /mcp:<道具名 または method>`。決まった経路・道具名・method だけで、それ以外は `{unknown}`）・呼び手の種類（`token:<client名>`・`mcp:<client名>`・stdio の `mcp:local/<MCP client の名乗り>`・`screen`・`anonymous`）・状態（status と error code）・日ごとの回数・時間の合計と最大・応答の大きさだけ。題名・本文・検索語・ID・端末名は残さない。1つの要求は1行で数える。全権 token の要求（Tasken 自身の部品）は MCP の行と二重になるので数えない。同期・Export・Snapshot の対象外で、1年より古い日は消える。

## AI作業ログの時間表示

日次 Activity は人の活動と AI の作業を同じ時刻軸で扱い、週表示は補助とする。タスク関連付けの追加／解除は reference の既存 mutation だけを使い、AI の作業や Task の完了状態を変更しない。AI の作業が入る道は 2 つだけ: AI が自分で書く 1 件（`tasken.report_work`）と、本人が登録した保存先のログから Desktop が拾う 1 件（下の節）。hooks と、ファイルを選ぶ手の取り込みは無い（#751）。ログからは終わったのか止まったのかが分からないので、拾った物の状態は「途中」とし、turn の終わりを完了へ変換しない。

同じ日に表示するTaskのAI作業区間に `source_session` があり、収録済みSessionのIDと一致する場合は、そのSessionの関連活動へまとめる。同じ作業をTaskとSessionの二本の区間として重ねない。一致するSessionがないTaskの作業区間は単独で保持する。

AI の作業は、古い会話（`agent_session`）も新しい記録（`agent_work_record`）も、1 つの読み替え（`src/shared/agentWorkCard.ts` の AgentWorkCard）を通して同じカードで読む（#751）。日誌・テーマ・近況・日誌の出力・MCP の読む道具・Mobile Gateway は、このカードだけを読む。古い会話の読み替えは、移行で会話を畳んだ後に消す。
Debrief内のAI作業ログは、PCでは週／日カレンダー、狭い幅では日別リストで同じカードを読む。従来のTasken Activityと同じJST（Asia/Tokyo）で日境界と時刻を統一し、ブラウザ／OSのタイムゾーンが違っても表示は変わらない。タイムゾーン名を画面に明示する。
古い会話の終わりは、記録された終わりと `observation.observed_until` の早い方にする。終わりの分からない会話を現在まで伸ばしたり、済んだと推定したりしない（状態は「途中」）。観測情報も終わりもない会話は開始時点の点で示す。ログの観測が無く進行中と記録された会話だけ、現在まで表示できる。始まりの無い新しい記録は、終わりの時刻の点で示す。
棒は開始〜終わりの経過区間であり、待機・背景処理・重複を含み得る。実働時間と費用は取得していないので、表示しない。最小クリック高は時間の長さを意味しない。
カード = 時刻・AI の印・リポジトリかテーマ・要約 1 行。開くと、変えた物・確かめたこと・残り（と、依頼・気づき）。AI の印は藍。ログから機械が拾い上げた物（`basis = log_pickup`）は薄い墨の点線にする。値がない欄やリンクを捏造しない。途中の依頼と回答、判断、次の提案は出さない（新しい記録が持たない）。
関連Taskは、古い会話は既存Referenceの投影から、新しい記録は記録が持つIDから開く。関連付けを後から足せるのは古い会話だけ（新しい記録は書き換えない）。カードは本人が消せる（消した印。すぐ後の「元に戻す」で戻せる）。

### AI のログからの拾い上げ

本人が登録した保存先（Codex の sessions、Claude Code の projects）のログから、Desktop が **静かになった会話だけを 1 件ずつ** AI の作業（`agent_work_record`、`basis = log_pickup`）として書く（#751）。NAS には読むログが無いので、Desktop だけで動く。

- **静か** = 最後の動きから 60 分（`AGENT_LOG_QUIET_MS`）。ファイルの更新時刻が 60 分以内のログは開かない。更新時刻が古くても、ログの中の最後の時刻が 60 分以内なら待つ。Codex・Claude Code のログには会話の終わりの印が無いので、終わりの印では判定していない。会話が伸びるたびに読み直して書き換える事はしない（1 件は 1 回だけ書く）。
- **書く物** = 会話の ID・始まりと最後の動きの時刻・最初の依頼の先頭（160 字まで）・最後の回答の先頭（400 字まで）。変えた物・確かめたこと・残り・気づきは空にする（ログから推測で作らない）。作業場所（cwd）は登録済みのリポジトリに直すためだけに使い、保存しない。会話名・処理時間・途中の依頼と回答は残さない。
- **書く口** = Core の AI の作業の入口（`AgentWorkRecordService.pickUp`）。Desktop の中からだけ呼び、HTTP の受け口には出さない（根拠 `log_pickup` と書き手 `Tasken log pickup` を、外の client が名乗れない）。案も来歴も作らず、同期の差分は 1 つ。
- **同じ作業を 2 回数えない**（判定は Core の 1 か所。`AgentWorkRecordService` の `writeObserved` と `planAgentWorkRange`）。数える前の記録は、同じ AI（表記と別名をそろえた `client_kind`）の同じ会話の記録と、同じ会話の古い会話（`agent_session`。移行までの間）。本人が消した物を含む（消した作業を拾い直さない）。その終わりがログの最後の動きの 10 分前より後なら書かない。それより長い続きがあれば、続きの分だけを書く（始まり = 前の記録の終わり）。記録の ID は「会話 ＋ 範囲の始まり」から作るので、読み直しても 2 件にならない。
- **予備の判定**（AI は自分の会話の ID を知らない事が多い）: 会話の ID を書かなかった AI の記録（`basis = ai_report`、`source_session_id` 無し）が、同じ AI・同じリポジトリにあり、終わりどうしが 10 分以内なら、同じ作業と見て書かない。これは「書かない」を決めるだけで、始まりは削らない。会話の ID を持つ記録と、拾い上げどうしは、この判定に入れない（同じリポジトリの別の worktree で並んで動く会話は、どちらも丸ごと残る）。
- **並べ方**（`listAgentWorkCards`）: 記録が古い会話の範囲を覆う時（終わりが会話の最後の動きの 10 分前より後で、始まりが無いか会話の始まり以前）だけ、古い会話のカードを隠す。続きだけを書いた記録は、会話と両方を並べる（続きの記録は会話の依頼も残りも持たないので、隠すと引き継ぎが消える）。

PC の保存先設定と「このファイルのこの大きさ・更新時刻は、もう見た」の控えは userData/agent-log-sources/sources.json に置き、正本 Entity や共有同期へ保存しない。控えを無くしても、Core が同じ会話を 2 件にしない（読み直しの手間が増えるだけ）。サービスを選択して候補を示す段階では走査しない。利用者が場所と、保存する物、現在の Tasken / 共有同期先を確認してから登録する。拾った記録も共有同期設定の対象であり、生ログ全文を転送しない。同期先の変更後は再確認まで書くのを止める。

ファイルは読み取り専用のストリームとして解析し、選択したルートを越えるリンク・subagents を辿らない。`.jsonl` と、Codex が古い会話を圧縮した `.jsonl.zst`（zstd。Node の zlib で展開しながら読む）を読む。128MB/file、8MB/line、10000 files、100000 entries、depth 6、512MB/run、120秒の上限を守る。圧縮されたログの大きさは、どちらの上限も展開後の大きさで数える。静かになった後も壊れたままの最後の行（改行で終わっていない書きかけ）は捨てて読み、破損行・展開できない圧縮の診断へ原文を含めない。消えたログから Entity を削除しない。subagent・レビュー用の thread は親の会話の一部として、単独では拾わない。画面への知らせは、1 回の読み取りの終わりに 1 回だけ出す（初めての読み取りで数百件を書いても、画面の読み直しは 1 回）。

各保存先は更新時刻の新しいファイルから読む。形式不正が確定したログは mtime/size・理由だけを控えへ保存し、不変の間は診断を残して再読込を省く。ファイル変更、同じ保存先の再確認・登録時に再試行する。権限・一時的な読込失敗、保存の失敗は再読込を省かない。これにより古い不正ログだけで毎回の読込上限を消費し続けない。

Codexの同じSession IDの `session_meta` が重複しても、開始時刻が一致すれば単一の会話として読む。異なるSession IDや別サービスが混在するファイル、同一IDで開始時刻が矛盾するファイルは拾わず、読込エラーを示す。

定期の拾い上げは初期無効、明示有効時だけアプリ起動中に5分ごとで、常駐サービスやOSの自動起動を追加しない。

古い会話の受け口（`/v1/commands/propose-agent-session`）は、会話も案も、もう作らない。送ってくるのは古い hooks がまだ入っている PC だけで、その hook は誤りでない返事を受けると手元の控え（`agent-session-observations`）を消す。控えはその会話の最後の写しになりうる（送れずに溜まっていた会話、ログの拾い上げの対象でない AI）ので、受け口は捨てずに、終わった会話（capture）を AI の作業 1 件に畳んで書いてから「受信済み」と答える。畳み方は古い会話の読み替え（`agentWorkCardFromSession`）と同じで、字数と件数は記録の上限に切り、根拠は `folded`、ID は前の版が会話に付けていた ID。記録の終わり（と重複の判定に使う終わり）は、最後の回答の時刻（`response_checkpoints` の最後。無ければ `ended_at`）にする。hook の `ended_at` は client を閉じた時刻で、それを使うと、ログから拾ってある会話に動いていない時間だけの続きができる。端末の場所の形の「変えた物」と無い ID の結び付けは捨て、秘密の形の文は伏せる。記録に書けない形は断らずに直す（200 字を超える・場所の形の会話の ID は、同じ ID から必ず同じ値になる形に縮める。始まりが最後の動きより後なら始まりを寄せる）。断ると hook は控えを残して送り続けるため。書いた時は画面へ知らせる。拾い上げの書き手の名前を名乗る `caller` だけは断る。同じ作業を 2 回数えない判定は拾い上げと同じ所を通る（もう数えてある会話・本人が消した会話は書かない）。開始と終了（start・finish）は受けるだけで書かない。各 PC で hooks を外したら（README の「古い hooks を外す」）、受け口ごと消す。

拾い上げの書き手の名前（`Tasken log pickup`）は、外の client が名乗れない。`record-agent-work` はその `caller` を断り、`undo-change` はその名前での取り消しを断る（stdio の `caller` は自己申告なので）。
