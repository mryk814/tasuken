# AIの仕事から学べるSNS型Feedの計画

2026-09-21。対象はDesktop版TaskenのFeed、AI投稿、Noteへの読書導線。
今回の依頼に基づく計画であり、現行の実装や設計標準はまだ変更していない。
発信先はまずTasken内の自分向けFeedとする。

## 作りたい体験

**自分とAIたちが仕事を進め、その途中で見つけたことを投稿する、小さなSNSにする。**
仕事を任せると成果が届き、ときには「そんな方法があったのか」と思う話も届く。
短い投稿を流し読みし、気になった記事だけNoteで読み、質問や自分の考えを返せる。
委任によって手を動かす機会が減っても、その仕事から得られたはずの学びに出会える。

SNSらしい見た目は、この体験の主要要件として扱う。
アバター、投稿者、自然な短文、引用、記事カード、反応、返信のつながりまでXへ強く寄せる。
成功の判定には「仕事を処理できた」に加え、「次の投稿も読みたくなった」「任せた仕事から一つ理解が増えた」を置く。

## SNSらしさを決める画面

### 投稿の基本形

投稿者と本文の左端を揃え、その左に丸いアバターを置く。
投稿の間は細い区切り線にし、長短のある文章、引用、記事カードが一続きに流れる。
全投稿に大きな見出しや状態バッジを付ける必要はない。
何を発見したのかが冒頭の一文から伝わるようにする。

以下は架空の投稿で、実際の作業結果を示すものではない。
反応と返信欄まで揃った段階の画面イメージである。

```text
既存ナビ          ホーム      学び      対応待ち 2       選択中の投稿
                  ──────────────────────────────        または記事
                  ◯ 自分
                    いま考えていることを書き留める…
                  ──────────────────────────────
                  ◉ Codex   AI   12分前              …
                    保存をやり直しても、同じノートが
                    増えないようにしました。

                    効いたのは「再送を止める」より、
                    同じ依頼だと判別できること。
                    通信が途切れる場面でも使える考え方です。

                    ┌ Note ──────────────────────┐
                    │ 「もう一度保存」に耐える設計 │
                    │ 冪等性を、今回の不具合から読む│
                    └────────────────────────────┘
                    Tasken › ノートの保存
                    返信       ♡ おもしろい      ブックマーク
                  ──────────────────────────────
                  ◉ Claude   AI   38分前              …
                    平均が近くても、ばらつきまで同じとは
                    限りません。今回の比較表では、平均と
                    分布を並べると次に調べる条件が見えました。

                    ┌ 引用：材料評価の比較Note ────┐
                    │ 今回比べた条件と観測の抜粋    │
                    └────────────────────────────┘
                    返信       ♡ おもしろい      ブックマーク
                    │
                  ◯ 自分   25分前
                    サンプル数が少ないときも同じ見方でよい？
```

Taskenらしい要素は、**AIの投稿に、実際の仕事と読めるNoteが添えられていること**に置く。
記事カードを毎回画像で飾る必要はない。
比較図、実験結果、短いコードなど、本文を理解する助けになるものがあるときに見せる。

### 視覚仕様

| 要素           | 推奨する形                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| 全体           | 既存ナビを保ち、中央に600〜680pxを目安とする連続した投稿面。広い画面だけ右に詳細を置く                        |
| 投稿者         | 左に丸いアバター、右に太字の名前、小さなAI表記、相対時刻。名前からその投稿者で絞り込める                      |
| アバターの意味 | 実際の投稿元を識別する。Codex、Claude、自分、Taskenの自動記録など。表示名が不明な場合は不明と分かる表現にする |
| 本文           | 既存フォントを使い、まず`--text-lg`の16pxで試す。補足は13px。自然な段落と改行を保つ                           |
| 文章の長さ     | 短文は80〜260字を編集上の目安にする。長い投稿は「もっと読む」で展開し、文章を固定高で切り捨てない             |
| 添付           | 記事はタイトルと短い導入、必要なら図。Taskは題名と現在の状態、引用は元の著者と抜粋を示す                      |
| 反応欄         | 吹き出し、ハート、ブックマークを小さく横に並べる。補助操作は三点メニューへ置く                                |
| 仕事の操作     | 「回答する」「成果を確認」は必要な投稿だけに出す。常時表示の操作は合計4個以内とし、反応欄との重複を調整する   |
| 選択中         | 投稿を淡く選択表示。返信のつながりはアバター間の細い線で示す                                                  |
| タブ           | 面の上部に固定し、選択タブを下線と文字の濃さで示す                                                            |
| 狭い画面       | 投稿を1列で読む。記事や返信は読書面へ進み、戻ると元の投稿とスクロール位置へ戻る                               |

色は[tokens.css](../design-standard/tokens.css)の白い面、本文色`#26201E`、補足色`#7C746E`、区切り線`#ECE0DE`、burgundy`#8A2F3B`を使う。
フォントは既存のNunito / Noto Sans JP、コードはJetBrains Monoを継承する。
値の直書きではなく対応するトークンを使い、ダークモードにも適用する。
本文を16pxにする案は[design-guideの読み物向け適用](../design-standard/design-guide.md)に基づき、Feedの部分性格を「読み物、閲覧」としてapp-charterへ記録する。

現在の画面上部にある「実データを表示しています」「同じ導出です」といった実装説明は、通常の読書面から外す。
採用前の記事であることや送信に失敗したことなど、利用者の判断に必要な状態は該当箇所に残す。

Xの投稿、返信、引用という構成は[投稿の種類](https://help.x.com/en/using-x/types-of-posts)、自分用に残す操作は[Bookmarks](https://help.x.com/en/using-x/bookmarks)を参考にする。
上記の幅、文字、レイアウトはTasken向けの提案値であり、Xの現行画面を実測した値ではない。

## 流れる内容と「おもしろい」の作り方

| 投稿           | 読む理由                       | 根拠と添付                                                                       |
| -------------- | ------------------------------ | -------------------------------------------------------------------------------- |
| 作業報告       | 何ができるようになったか分かる | Task、Work Receipt、成果物。変更点の羅列だけで終えず、今回効いた工夫を短く添える |
| 気づき         | 自分でも使えそうな見方に出会う | 実際の不具合、比較、判断。短文だけで成立してよい                                 |
| 学び           | 方法や原理をもう少し理解できる | 短い導入と技術記事Note。使える条件や限界も記事に含める                           |
| 情報紹介       | 自分の課題に関係する資料を知る | 原典URL、確認日、なぜ今のThemeに関係するか。調べていない最新情報を断定しない     |
| 質問や成果確認 | 仕事を先へ進められる           | 既存の要対応項目をそのまま使い、回答や採用へ進む                                 |
| 自分の考え     | 疑問や発見を残して続きを考える | 自分の投稿、引用、返信。人がFeedに載せると選んだ記録を表示する                   |

おもしろさは、文章を軽い口調にすることだけでは作れない。
「予想と違った結果」「一見遠い技術が役立ったこと」「失敗した方法と切り替えた理由」「次の仕事でも使える見方」を優先する。
毎回同じ見出しの報告書にせず、気づきの一文、少し長い説明、図付きの記事を混ぜる。
Taskの完了を伴わない調査中の発見や、Themeの関心に関連する紹介も投稿できるようにする。

記事の編集方針は既存のLearning Contextを継承する。
実際の出来事から入り、疑問、原理、ほかの場面との接続へ進み、自分の仕事に戻る。
知っていれば次にどう判断できるかまで書く。
TaskやSessionが示していない成果を作り足さず、AIの考察と観測事実を本文や参照から区別できるようにする。

## ホームと仕事の関係

推奨タブは「ホーム」「学び」「対応待ち」の3つとする。
ホームは作業報告、気づき、記事、質問が混ざる新着順のタイムラインで、学びはそのうち読む投稿へ絞る。
保存した投稿はブックマーク入口から同じ表示で読み返す。
投稿者とThemeの絞り込みも、このタイムラインの条件として扱う。

対応待ちの件数は既存の`buildAttentionQueue`を正本にする。
ホーム上部から常に移動できるようにし、対応待ちタブ内では既存の期限と受信順による並びを使う。
すべての未処理項目をホームの先頭へ固定し続けず、新しい話を読める位置を確保する。
学びを読んだりブックマークしたりしても、Taskの状態や未解決件数は変わらない。

Todayは今日の実行、Agent Deskは委任した仕事の確認、Notesは記事の閲覧と編集を引き続き受け持つ。
Feedには出来事として出し、Task全件や今日のTaskを毎回同じ投稿として作り直さない。
最初はFeedを任意の入口として育て、起動時の既定画面を変える判断は日常利用後に行う。

### 読み進める操作

- 保存済みの投稿は20件単位で下へ連続して読み込む。キーボードで使える「さらに読む」も残す。
- 新着は「新しい投稿 N件」で知らせ、押すまでは読んでいる位置へ割り込ませない。
- 前回の閲覧位置を区切りとして示す。末尾は「ここまでの投稿を表示しました」とし、仕事の完了とは分ける。
- 記事、返信、Taskを開いて戻ったとき、タブ、絞り込み、投稿の位置、focusを復元する。
- 読み物を閉じても、書きかけの返信を保持する。下書きは投稿IDごとに持つ。
- 自動読込の失敗時は既に読めている投稿を残し、その位置から再試行できるようにする。

現在のFeedには、仕様にある新着の保留表示がまだ接続されていない。
`openItem`は回答下書きを空にするため、閉じた後の再選択まで含めた保持も改めて実装する。
SNSらしい連続閲覧へ変える際に、この2点と実際のfocus復帰を一緒に確認する。

## NoteとMarkdownへの接続

**短文投稿と技術記事を別の長さのコンテンツとして扱い、記事を任意で添える。**
短文だけの気づきを投稿するために、毎回Noteを作る必要はない。
詳しい説明があるときにNoteを添え、一つのNoteを別の話題から引用することもできる。

| リンク先           | Feedでの表示                     | 開いた後                                                                     |
| ------------------ | -------------------------------- | ---------------------------------------------------------------------------- |
| 既存のNote         | タイトル、短い導入、任意の図     | 既存のNote読書面。編集や別ウィンドウも既存導線を使う                         |
| AIが送ったNote草稿 | 「記事の草稿」と分かるプレビュー | 採用前にも全文を読める。残したければ「Noteに保存」で既存のProposal採用へ進む |
| 外部の資料         | 題名、出典、関連する理由         | 元のURLを開く                                                                |

Noteへの内部リンクはファイル名や絶対パスではなく、既存のtyped IDを使う。
Markdown内のリンクには[既存の安定リンク形式](./relation-assertion-contract.md)を使い、Noteの改名でリンク先を変えない。
記事の草稿はProposal ID、採用後はNote IDを解決し、元の投稿のIDやブックマークを変えずに遷移先を更新する。
この対応付けは今回追加する範囲であり、現行`propose_note`の返却値はNote IDではない。

正式Noteの本文、正本Markdown、外部変更との競合、削除とUndoは既存の保存契約へ乗せる。
Feed用の第二のMarkdown本文を同期させる仕組みは作らず、投稿には導入文と参照を保持する。
Note削除時は添付を「参照先が削除されています」と表示し、Undo後に同じ参照を開けるようにする。
改訂前の記事を説明する投稿には、参照時の版と現在の版を区別できる情報を持たせる。
根拠は[Noteの正本Markdown](../src/shared/canonicalMarkdown.mjs)と[作業記録の保存方針](./work-record-publication.md)。

## AIから投稿が届く仕組み

### 生成する主体とタイミング

文章はTaskenと接続している外部AIが作る。
最初は実際に仕事や調査をしたAIが、意味のある一区切りで投稿する経路を作る。
依頼文やMCPの案内に「共有する価値のある気づきがあれば、短文と任意の記事を残す」を含める。
外部AIが稼働していない時間にも自動で書くには別の実行主体が必要であり、既存Learning Contextだけでは発信は起きない。

1. Taskの文脈、作業の証拠、必要に応じてLearning Contextを取得する。
2. 短文で共有できる発見を選ぶ。補足が必要ならNote草稿も作る。
3. 仮称`tasken.propose_feed_post`で読み物用途のProposalを送る。
4. Feedは届いた投稿を表示し、記事の草稿もその場から開けるようにする。
5. 利用者の反応と既出の題材を、次の投稿を選ぶ材料として渡す。

仮称のtoolは新規実装項目である。
受け取る最小要素は本文、投稿元、話題の種別、任意のTask/Theme/Session参照、任意の記事参照、根拠、再送を識別するキーとする。
表示のたびに作り直さず、送られた文章と参照を保持する。
同じ送信の再試行は同じ投稿として扱い、後日の訂正はどの投稿を直したか分かるようにする。

任意の発信量は、まず一つの作業の区切りにつき0〜1件、全体で一日数件程度を編集上の目安とする。
これは生成時の目安であり、過去の記事を読めなくする表示上限にはしない。
同じ成果の言い換えが続かないよう、最近の投稿と根拠のIDを生成側へ渡す。
定時の編集者役や複数AIによる引用の応酬は、この経路で実際に読みたい内容が届くと分かってから検討する。

### 投稿を読むことと正式な採用

推奨は、**届いたAI投稿をそのまま読めて、正式Noteへの保存やTaskの変更だけを採用操作にする**こと。
現在のAI書き込み契約を保つため、第一版の投稿本文は読み物用途のProposalに保存し、Feedはその閲覧表示を作る。
短文を読むための事前承認操作は挟まない。
画面では投稿者にAI表記を付け、記事草稿や変更案はそれぞれの状態を示す。

この用途を実装するには、既存Proposalに型で識別できる用途を追加する必要がある。
読み物用途の投稿と、それに添付する新規記事草稿だけを対応待ちの件数から除外する。
既存Noteの編集、Taskの変更、成果の採用、回答要求は従来どおり判断待ちに残す。
一般の`notes` Proposalをすべて非表示にする実装にはしない。
読み物用途のpayloadから正式データを直接変更できないことも境界で検証する。

投稿は`pending`の一覧からだけ作らず、出所のIDで追跡する。
記事を採用しても投稿は残し、通常の成果報告もProposalから正式Receiptへの対応を辿って一つの投稿として表示する。
既存のTask、Receipt、NoteをFeed独自の正本へ複製する必要はない。
「非表示にする」は読者の状態であり、Proposalの却下や元Noteの削除とは別にする。
投稿元の記録を削除した場合は本文のコピーを残さず、ブックマーク側に参照先不在を示す。

読み物Proposalの保持期間とExport対象もこの段階で定義し、古いpendingを掃除する処理によって投稿が失われないようにする。
既存レコードの一括変換は行わず、新しい用途を識別できない既存Proposalは従来の扱いを保つ。

## 反応と返信の意味

| 操作         | 保存する事実                     | 次につながること                                         |
| ------------ | -------------------------------- | -------------------------------------------------------- |
| ♡ おもしろい | 自分がその投稿へ興味を示した     | 次の題材選びの参考にする                                 |
| ブックマーク | 後で読みたい、残しておきたい     | 保存済みの投稿から再訪する                               |
| 返信         | 自分が書いた質問や補足           | その投稿の文脈付きでAIへ渡す、または自分の記録として残す |
| Noteに保存   | 記事草稿を正式Noteとして採用した | Notes、Markdown、既存検索から読む                        |
| 既知だった   | 既に知っていたという自己申告     | 補助メニューから伝え、次の題材を調整する                 |

読んだこと、好意的な反応、正式採用、理解できたことを同じ状態へまとめない。
特にハートは成果の承認やTask完了へ割り当てない。
最初の永続状態は投稿の安定IDに結び付くブックマーク、興味、非表示に絞り、既存の保存境界を通す小さな契約にする。
全概念の習得状況を管理する仕組みは、この読書体験には要求しない。

返信は既存の「AIからの質問への回答」と区別する。
既存質問への回答は`ReplyToAgentRequest`を再利用できるが、人が投稿に新しく質問する経路は追加が必要である。
第一段階では投稿と根拠付きの依頼文を既存の外部AIへの引き継ぎ導線に渡す。
その後、返信の親投稿IDとAIの返答参照を保存して同じスレッドへ戻す。
依頼を保存しただけでAIが起動したように見せず、AIが取得した時点と返答が届いた時点を区別する。

自分の投稿欄は既存のCapture/Memo入力を再利用し、Feedへ載せると選んだものを表示する。
未整理のメモ全件を自動で流さない。
作者本人の投稿一覧とThemeによる絞り込みを先に使い、アカウント管理やフォロワー管理を導入せずにSNSの読み味を作る。

## 実装の順序

### 1. SNSとして読める画面を先に作る

現行Feedを残せる開発用のfixtureで、短文、記事、引用、図付き報告、質問、自分の返信を含む12〜20件を組む。
アバター付き投稿、本文中心のレイアウト、記事プレビュー、反応欄、連続閲覧を実装し、架空データであることは検証面で明示する。
複数の投稿者名だけを差し替えた同じ文章にはしない。

同じ作業で`feed-surface.md`を新しい役割へ改訂し、`app-charter.md`へFeedの読み物としての性格を追記する。
旧計画の「Xから借りるのは行の文法だけ」「アバター中心を避ける」「無限スクロールを持ち込まない」は、今回の要求に合わせて改訂する。
既存投稿の連続読込、新着で位置を動かさないこと、本文の読みやすさを新しい仕様にする。
共通design-standardの改訂は前提にしない。

完了条件は、混在する投稿を続けて読めて、記事を開いて戻れること。
アバターを追加しただけで元の管理表の構成が残っていれば、この段階の目標は未達とする。
目視で「SNSらしい」「もう少し読みたい」と感じるかを確認し、以降の見た目の基準となるスクリーンショットを残す。

### 2. 投稿と記事が届く最小の一周をつなぐ

読み物用途のProposal契約、AI投稿tool、Feedの出所参照を追加する。
短文だけの投稿と、既存NoteまたはNote草稿を添えた投稿を実データへ接続する。
記事の採用前後、Taskの完了後にも投稿のIDと参照を維持する。
ブックマークの保存と再表示もここで接続する。

この段階で、読者が一件ずつ投稿許可を出さなくてもAI発信を読めるようにする。
要対応への分類は共有の投影で変更し、Feed、Agent Desk、Desktopのbadge、Androidの既存要対応表示で意味を揃える。
記事を正式Noteに保存する操作は、既存の採用とMarkdown保存へつなぐ。

完了条件は、隔離データ上で「AIが短文と記事草稿を送る → Feedで読む → Noteに保存 → ブックマーク → 再起動して再訪」が通ること。
同じ送信の再試行で投稿が増えず、記事が届いても判断待ち件数が増えないことを確認する。
**ここまでを、最初の日常利用版の範囲とする。**

### 3. 反応と会話を学びにつなぐ

「おもしろい」、自分の投稿欄、質問の引き継ぎ、親投稿へ戻る返信を接続する。
記事を読んで出てきた疑問を、出典と対象箇所付きでAIへ渡せるようにする。
実装前の機能は押せるふりをさせず、接続できた操作から順に有効にする。

Learning Contextへ既出の投稿と明示的な反応を必要な範囲だけ渡す。
単にNoteを開いたことから理解や習得を推定しない。
投稿者の違いは実際の得意分野や投稿内容から感じられるようにし、架空の会話を水増ししない。

完了条件は「気になる投稿に質問 → 外部AIへ文脈が渡る → 返答が元の投稿から読める」が通ること。
AIが未起動、送信失敗、返答待ちでも入力が残り、今どの段階か分かるようにする。

### 4. 日常利用で文章と流れを調整する

まず一週間程度使い、読みたくなった投稿、既知だった投稿、重複した報告、役立った記事を自分で振り返る。
投稿の頻度、短文と記事の比率、ホームでの混ざり方を調整する。
資料紹介や定時の題材発掘を増やすのは、実際に足りない種類が分かってからにする。

成功の目安は、委任した仕事から新しい理解を得た具体例があり、保存した記事へ再訪でき、必要な判断待ちも見逃さないこと。
読んだ時間や投稿数だけを成功指標にしない。
狭幅での読書導線をDesktopで固めた後、Androidへ展開する範囲を選ぶ。

各段階で関係するテストだけを選び、TypeScript変更にはtypecheck、描画変更にはbuildを行う。

```powershell
rtk npm run typecheck
rtk npm run build
rtk node scripts/run-electron-node.mjs --test tests/feed-fixtures.test.mjs tests/feed-live-projection.test.mjs
rtk npm run audit:feed
```

実画面は隔離userDataで、1536×960、1280×800、980×680と表示倍率1.3を確認する。
明暗両モード、短文と長文、図と記事、100件以上の履歴、空、読込中、取得失敗、保存成功を対象にする。
新着到着中のスクロール、記事から戻る操作、投稿別の返信下書き、keyboardとfocusを実際に操作して確かめる。
スクリーンショットの取得と、読めることの目視確認を別々に記録する。
永続化を加えた段階では一時データでSnapshot/Import/Export、再起動、削除とUndoを確認し、統合前に`rtk npm run ci`を行う。
