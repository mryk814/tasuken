# Feed surface の設計（SNS型の読む面）

Tasken Feed の見た目・並び順・操作の意味。
**2026-09-21の新しい計画（[feed-learning-sns-plan-2026-09-21.md](./feed-learning-sns-plan-2026-09-21.md)）で役割を改訂した。**
Feedは「対応待ちの一覧」から、**委任した仕事から得られた学びを読む面**へ変わる。
判断待ちの正本は引き続き `buildAttentionQueue` で、Feedの「対応待ち」タブはそのprojectionである。

- 用語と採用contract: [agent-collaboration.md](./agent-collaboration.md)
- 実装する契約: [agent-work-contract.md](./agent-work-contract.md)
- 外部6製品の比較（旧計画の根拠）: [feed-six-product-comparison.md](./research/feed-six-product-comparison.md)
- アプリの性格: [app-charter.md](./app-charter.md)（Feedは「読み物・閲覧」）

実装: `src/renderer/src/features/workspace/pages/FeedPage.tsx`、投稿の型・実データの写像・開発用fixtureは `src/renderer/src/features/workspace/lib/feedPosts.ts`、要対応の射影は `src/renderer/src/features/workspace/lib/feedProjection.ts`、旧・行中心の規則は `src/renderer/src/features/workspace/lib/feedFixtures.ts`、見た目は `src/renderer/src/styles/feed.css`。
投稿は外部AIが `tasken.propose_feed_post`（`payload_type: "feed_posts"`）で送り、`src/main/services/aiProposalAcceptanceService.ts` と `src/shared/contracts/task/attentionQueue.ts` が要対応から外す。読者の印は `feed_reaction` Entityとして保存する。

---

## 1. この画面が答える問い

**任せた仕事から、何を学べるか。**

FeedはTaskの一覧でも管理画面でもない。一つひとつの投稿が「出来事」または「判断」で、
読むことで次の判断ができる形にする。Task全件、毎回同じ期限警告、raw logは主役にしない。
作業の正本はTask・Work Receipt・Noteのままで、Feedはそれらを**投稿として読ませる投影**である。

## 2. 責務の比較

| 画面         | 答える問い                                 | 主な操作                                   | 主役にしない情報                       |
| ------------ | ------------------------------------------ | ------------------------------------------ | -------------------------------------- |
| Feed         | 何を学べるか、何に反応するか               | 読む、開く、返信、保存、対応する           | Task全件、毎回同じ期限警告、raw log    |
| Today        | 今日、自分が何を実行するか                 | 着手、完了、扱う日の変更                   | AIの全進捗、接続管理、未整理入力の全件 |
| Agent Desk   | 任せた仕事がどこまで進み、何を待っているか | 回答、成果確認、報告採用、委任内容確認     | token数、モデル比較、実行コンソール    |
| ToDo / Theme | 仕事全体の内容・所属・日程をどう管理するか | 編集、分類、計画、検索                     | Feed用の独自Taskコピー                 |
| Notes        | 記事を読む・書く                           | 閲覧、編集、別ウィンドウ                   | Feedの閲覧位置                         |
| Activity     | いつ何が起き、どの記録を根拠に振り返るか   | 日時から記録へ移動                         | 現在の判断待ちの別管理                 |
| Inbox        | 残した入力をどう整理するか                 | Task化、Note化、未整理記録のFeed掲載、整理 | Feedの既読処理                         |

- 判断の操作は**同じ要対応項目**を開き、回答・採用は既存Commandへ繋ぐ。
- 読む・保存する操作は、**Taskの状態と未解決件数を変えない**。
- 要対応件数のbadgeはAgent Deskへ集約し、Feedと二重に付けない。Feedの「対応待ち」タブは同じ数を出す。

## 3. 投稿の基本形

```text
◉ Codex   AI   12分前   [✦ 気づき]              …
  保存をやり直しても、同じノートが増えないようにしました。

  効いたのは「再送を止める」より、同じ依頼だと判別できること。

  ┌ AI記事 ───────────────────────────┐
  │ 「もう一度保存」に耐える設計         │
  │ 記事の草稿（採用前）                 │
  └───────────────────────────────────┘
  Tasken › ノートの保存                [記事を読む]
  💬 2   ♡   🔖
──────────────────────────────────────────
```

- 投稿者と本文の左端を揃え、左に丸いアバター（画像ではなく頭文字）を置く。
- 投稿の間は**細い区切り線**。全投稿へ大きな見出しや状態バッジを付けない。
- 返信は投稿列へ並べず、選んだ投稿の**右スレッド**で読む（§6.5）。

### 見た目の規則

| 項目       | 規則                                                                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 全体       | 既存ナビを保ち、中央に640〜720pxの連続した投稿面。会話を開くと右へ360〜420pxを足す                                                                                                     |
| 投稿者     | 左にアバター、右に太字の名前、AI表記、相対時刻。名前を押すとその投稿者で絞り込む                                                                                                       |
| アバター   | 出所ごとに**形と色と頭文字**を変えて識別する。サービスロゴの公式アセットは同梱しないため、ロゴを模した図は作らない                                                                     |
| 種別       | アイコンだけでは種類が読み取れないため、**アイコンと短い語を併記**する（気づき・学び・情報紹介・質問・作業報告）                                                                       |
| 本文       | `--text-lg`(16px)、行間1.75。補足は13px。段落と改行を保つ                                                                                                                              |
| 文章の長さ | 短い投稿は80〜260字を目安。長い投稿は**もっと読む**で展開し、固定高で切らない                                                                                                          |
| 添付       | 記事はタイトルと短い導入、Taskは題名と現在の状態、引用は元の著者と抜粋、外部は出典と確認日                                                                                             |
| 図         | 理解の助けになる投稿だけに置く。毎回飾らない。見出しで内容を説明する                                                                                                                   |
| 入口       | 画像は既存Artifactを参照し、外部リンクはURLだけでも完成させる。投稿一件の主画像は一枚まで（§4.5）                                                                                      |
| 反応欄     | 返信・おもしろい・ブックマークを**既定のアイコン**で小さく横に並べ、補助操作は三点メニューへ置く。ONの状態は色だけでなく**塗りつぶしアイコン**で示す（返信はスレッドが開いているとき） |
| 仕事の操作 | 「回答する」「成果を確認」は必要な投稿だけに出す。常時表示は合計4個以内                                                                                                                |
| タブ       | 面上部に固定し、選択タブを下線と文字の濃さで示す                                                                                                                                       |
| 実装説明   | 読む面に出さない。採用前・送信失敗など**判断に必要な状態**だけを該当箇所へ残す                                                                                                         |
| 色         | `tokens.css` の面・本文・補足・区切り線・burgundy。値の直書きをしない                                                                                                                  |
| 動き       | 新着の挿入・点滅・連続する読み上げをしない。`prefers-reduced-motion` を尊重する                                                                                                        |

本文は選択できる。行全体を巨大な `button` で囲まず、読む領域と操作領域を分ける。

## 4. 流れる内容（投稿の種類）

| 投稿           | 読む理由                       | 根拠と添付                                                                   |
| -------------- | ------------------------------ | ---------------------------------------------------------------------------- |
| 作業報告       | 何ができるようになったか分かる | Task、Work Receipt、成果物。変更点の羅列で終えず、今回効いた工夫を短く添える |
| 気づき         | 自分でも使えそうな見方に出会う | 実際の不具合、比較、判断。短文だけで成立してよい                             |
| 学び           | 方法や原理をもう少し理解できる | 短い導入と技術記事Note。使える条件や限界も記事に含める                       |
| 情報紹介       | 自分の課題に関係する資料を知る | 原典URL、確認日、なぜ今のThemeに関係するか。調べていない最新情報を断定しない |
| 質問や成果確認 | 仕事を先へ進められる           | 既存の要対応項目をそのまま使い、回答や採用へ進む                             |
| 自分の考え     | 疑問や発見を残して続きを考える | 自分の投稿、引用、返信。人がFeedに載せると選んだ記録を表示する               |

おもしろさは口調では作れない。「予想と違った結果」「一見遠い技術が役立ったこと」
「失敗した方法と切り替えた理由」「次の仕事でも使える見方」を優先する。
毎回同じ見出しの報告書にせず、気づきの一文・少し長い説明・図付きの記事を混ぜる。

### 4.5 画像と外部URL（フェーズ3）

投稿一件に添える入口は**一つ**とする。主画像は一枚までとし、複数の図が必要な説明は記事へまとめる。
画像は投稿の必須条件ではない。画像なしの短文も完成形とし、画像がない投稿を弱く見せない。

| 経路             | 主な用途                             | 実装                                                                            |
| ---------------- | ------------------------------------ | ------------------------------------------------------------------------------- |
| 既存Artifact     | 実験図、画面、作業成果、既存の説明図 | 投稿が `artifact_id` を参照し、検証済みの `tasken-media://artifact/<id>` で描く |
| 外部URL          | 参考記事、公式資料、論文             | URLカードを出し、取得できたOpen Graph画像を派生サムネイルにする                 |
| AIが作った説明図 | 概念比較、処理の流れ、記事の導入     | 記事の `article.images` として受け取り、既存の添付画像経路で保存する            |

- 画像には **実測・作業成果／参考元／説明図** の役割、短いキャプション、代替テキストを持たせる。
  役割が読めない画像は「実測」と断定せず説明図として扱う。
- 実測図とAIの説明図を同じ見た目で断定的に扱わない。根拠のない装飾画像、
  実在しない測定結果のグラフは投稿させない。
- 参照先のArtifactが無い・画像として読めない場合は、投稿全体を失敗させず
  **画像を表示できません**の一行へ落とす。本文はそのまま読める。
- 画像は切り抜かず全体を収めて見せる（`object-fit: contain`）。長い題名・URL・キャプションで
  横へはみ出さない。
- 画像生成を毎回行う仕組みは導入しない。画像生成できないAIも、本文・既存Artifact・
  外部URLだけで同じFeedへ投稿できる。

外部リンクカードは**URLだけでも完成状態**として表示する。メタデータ取得に失敗した場合は、
投稿者が付けた題名、ホスト名、URL、投稿者の一言へ安全にフォールバックする。
取得は、そのカードが画面に見えたときに一度だけ行い、結果は**正本ではない派生キャッシュ**として
扱う（オフラインでも投稿本文は読める）。

外部ページの取得はRendererから行わない。Main側の専用サービスだけが扱い、次を守る。

- 公開HTTP(S)だけを許可し、資格情報付きURLとtoken類のqueryを拒否する。
- 名前解決したアドレスを毎回検査し、loopback・private・link-local・CGNAT・multicastを拒否する。
  転送は自動追従せず手動で追い、**転送先でも同じ検査**を行う（3回まで）。
- 資格情報・Cookie・Refererを送らない。時間・HTMLサイズ・画像サイズ・MIMEを制限する。
- スクリプトを実行しない。画像は宣言されたcontent-typeを信用せず、実バイトのmagic numberで判定する。
- 取得結果はDB・Workspace・Exportへ書かない。消えても再取得できる。

記事へ埋め込む画像（`article.images`）は、`tasken.propose_note` と同じ
`tasken-upload://` プレースホルダー、同じ検証（形式・寸法・合計サイズ）、
同じ添付保存先を使う。保存前の記事と、利用者が「Noteに保存」した後のNoteは
**同じ画像ファイルを指す**（本文の `tasken-attachment://` は変わらない）。
採用の直前には画像の実在を確かめ、欠けていれば保存を止める。

## 5. 操作の意味

| 表示名                       | 対象と結果                                                                                | 変えてはいけないもの                  |
| ---------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------- |
| Feedへ投稿                   | 自分の記録をFeed専用の投稿として保存し、Feedへ載せる（Notesには残さない）                 | 未整理のメモを自動で流さない          |
| 未整理記録をFeedへ載せる     | 未整理のInbox記録をFeed専用の投稿として保存し、Feedへ載せる。元記録は出所を残して片付ける | Taskの状態、未解決件数                |
| 投稿を削除                   | 自分の投稿をFeed専用から消す（元に戻せる）                                                | Taskの状態、未解決件数                |
| 投稿を編集                   | 自分の投稿の本文を同じIDで直す（公開時刻・Theme・出所は変えない）                         | 投稿の表示とID                        |
| 返信                         | 投稿への短い返信を書く（保存する）                                                        | Taskの状態、未解決件数                |
| AIに聞く（接続済みAIへ残す） | 投稿と根拠を添えて接続済みAIへ質問を残す。押した時点ではAIを起動しない                    | 押した時点でのAI起動、回答の到達      |
| 外部AIに聞く                 | 質問と選んだ文脈だけをコピーする。Taskenは送信・起動を行わない                            | 送信の完了、文脈の自動付加            |
| 外部AIの回答を貼り付け       | 普段の外部AIの回答を、質問・出所・会話URL・自分の一言と一緒に元投稿のスレッドへ保存する   | Taskの状態、未解決件数、MCPの待ち状態 |
| 貼り付けを訂正               | 自分が貼り付けた回答・出所・補足を同じIDで直す                                            | 親投稿、他の返信、Noteの削除          |
| 返信を削除                   | 自分の返信を外す（元に戻せる）                                                            | 親投稿、他の返信                      |
| おもしろい                   | 自分用の印を付ける（保存する）                                                            | Taskの優先度、順位、未解決件数        |
| ブックマーク                 | あとで読み返す印を付ける（保存する）                                                      | Taskの状態、未解決件数                |
| 既知だった                   | 既に知っていたと伝える（三点メニュー、保存）                                              | 理解度の管理、Taskの状態、未解決件数  |
| ブックマーク（面）           | ブックマーク面で、保存済み／おもしろい／既知だったの印ごとに読み返す（表示のみ）          | 投稿の並び、印そのもの                |
| 記事を読む                   | AI記事・記事の本文を、既存のMarkdown描画で読む面を開く                                    | 開いただけでの採用                    |
| Noteに保存                   | AI記事を既存の採用経路で正式Noteにする                                                    | 投稿のID、ブックマーク、未解決件数    |
| Noteで読む                   | 保存済みのNoteを既存のNote面で開く                                                        | 投稿の表示とID                        |
| 元のFeed投稿を開く           | Notesから元の投稿へ戻り、その会話を開く（表示のみ）                                       | 投稿、返信、印、Noteの本文            |
| 回答する                     | 特定の質問へ人間の返答を保存する                                                          | Task本文の全文、別の質問              |
| 成果を確認                   | Task詳細を開く。採用は既存操作で行う                                                      | 開いただけでの採用やTask完了          |
| 今回は見送る                 | この投稿を今回のFeedから外す（保存する）                                                  | Task・Note・Proposalの正式な採否      |
| さらに読む                   | 20件単位で続きを読む                                                                      | 仕事の完了表示                        |

読む操作（返信・おもしろい・ブックマーク・既知だった・今回は見送る・記事を開く）は
**Taskの状態と未解決件数を変えない**。印は投稿の安定ID（`feed-reaction:<投稿ID>:<種類>`）に
結び付けた `feed_reaction` Entityとして保存し、取り消しはEntityの削除で行う。
同じ操作を繰り返しても増えない。

「既知だった」は**自己申告**として補助メニュー（三点）へ置き、次の題材選びの材料にする。
読んだこと・好意的な反応・正式な採用・理解できたことを同じ状態へまとめない（理解度は管理しない）。
外部AIは `tasken.get_feed_context` の `known_post_ids` から既知の題材を知り、同じ説明を繰り返さない。

「ブックマーク」面は、印を付けた投稿を**同じ表示のまま**読む表示の切り替えである。
初期表示はブックマークとし、「おもしろい」「既知だった」へ切り替えて絞り込む。
並び替えも投稿の複製もせず、ホームへ戻ると元のタイムラインへ戻る。件数のbadgeは変えない。
Noteへ保存した記事と投稿のブックマークは別の状態として見せる。

「Noteに保存」で採用したNoteを後から削除すると、添付は**参照先が削除されています**と示す。
AI記事の本文は投稿に残るので「記事を読む」は残し、正式Noteを開く導線と「Noteに保存」は外す
（採用済みのProposalは戻せないため、押しても失敗する操作を残さない）。
Noteの削除は既存の「元に戻す」で同じIDへ復元でき、そのときこの参照もまた開ける。

**既存Noteへの参照**（`payload.note_id`）は、投稿がNoteの中身を複製せずIDだけを持つ。
添付は題名をNoteの正本から出し、「参照しているNote」と示して「Noteで読む」で既存のNote読書面
（編集・別ウィンドウも既存導線）を開く。参照先のNoteを削除したときは、採用したNoteと同じく
**参照先が削除されています**と示し、開く導線を外す（「元に戻す」で復元すると、同じ参照からまた読める）。

返信は投稿のIDに紐づく `feed_reply` Entityとして保存する（第3段階）。
人が書いた返信とAIの返答を同じスレッドへ置き、**スレッドの中は古い順**に読む
（タイムライン全体は新しい順）。返信の削除はEntityの削除で、既存の「元に戻す」から復元できる。
投稿（読み物Proposal）を削除すると、その投稿への返信と印も一緒に外れ、復元で一緒に戻る。

「AIに聞く（接続済みAIへ残す）」は返信に `ai_requested_at` を付けて残すだけで、**押した時点ではAIを起動しない**。
外部AIは `tasken.get_feed_context` で未回答の質問と元の投稿を読み、
`tasken.answer_feed_question` で返答を返す。返答は `feed_replies` Proposalとして届き、
同じスレッドへ並ぶ。スレッドの印は「AIに依頼済み」と「回答あり」を区別し、
依頼しただけで回答が来たように見せない。

普段使う外部AI（M365 Copilot等）への往復はクリップボードで行い、Taskenからの送信・起動・自動取得はしない。
コピーは質問と選んだ文脈のプレビューだけを `clipboard.writeText` で渡し、添付Note全文・Task詳細・他のスレッド・ファイルパスは自動で付けない。
貼り付けは回答本文・質問・出所（未指定可）・任意の会話URL・自分の一言を確認してから、元投稿のスレッドへ `feed_reply`（`origin: "manual_paste"`）として保存する。
保存主体は人間、回答の出所は外部AIとして「自分が貼り付け · 出所」と示し、接続済みAIの直接返答と区別する。
回答内容・出所・会話URLは利用者提供であり、事実確認済みを意味しない。コピー・貼付で `ai_requested_at` を付けず、MCPの待ち状態を変えない。
既存MCP向け質問への手動回答の紐付け（待ちの解消）は初版の対象外。下書きは投稿別にlocalStorageへ保持し、保存前は正式返信にもMCP待ちにも出ない。
保存済みの貼り付けは同じIDで訂正でき、必要な回答・補足だけを既存Note作成画面へ渡す（人が確認して保存する）。

自分の投稿欄は**Feed専用の投稿（`feed_post`）へ保存**する。投稿はNotesに残さない。
Inboxの未整理記録は「Feedへ載せる」で同じFeed専用として保存し、
出所を残したまま元の記録を片付ける。FeedはFeed専用の保存分だけを「自分の記録」として読み、
**未整理のメモ全件を自動で流さない**。削除は既存の「元に戻す」で戻せる。
移行前のFeed印付きNoteは起動時にFeed専用へ移し、投稿IDと会話の対応を保つ。
アカウントやフォロワーの管理は持たず、投稿者の絞り込みとThemeの絞り込みで読み味を作る。

## 6. 並び順と読み進め

タブは「ホーム」「学び」「ブックマーク」「対応待ち」の4つ。アプリ全体の新しいページではなく、
一つのFeed内の表示切り替えとして扱う。

- **ホーム**: 新着順のタイムライン。作業報告・気づき・記事・質問を混ぜる。AIの非公開スコアを使わない。
- **学び**: ホームのうち読む投稿（学び・気づき）へ絞る。
- **ブックマーク**: 保存済み／おもしろい／既知だったの印で読み返す。
- **対応待ち**: `buildAttentionQueue` の未解決判断。並びは既存の期限と受信順。
  読み物と未読を件数へ加えず、回答・判断・成果確認だけを数える。
- 投稿者とThemeの絞り込みは同じタイムラインの条件として扱う。

読み進めの規則:

- 20件単位で下へ読み込む。「さらに読む」を残し、末尾は「ここまでの投稿を表示しました」とする。
- 新着は「新しい投稿 N件」で知らせ、**押すまでは読んでいる位置へ割り込ませない**。
- 閲覧位置は**投稿IDをアンカー**として保持する（前回の区切り線は置かない）。

### 6.5 会話（右スレッド）

ホームには親投稿と、**最新の返信一件の短い予告**、返信総数だけを出す。返信全件は投稿列へ並べない。

- 返信ボタンか予告を押すと、デスクトップでは右へスレッドを開く（広幅は並置、中幅は重ねる）。
- スレッドは親投稿、すべての返信（古い順）、入力欄で構成する。
- 通常の返信、「AIに聞く」、外部AIへのコピーと回答の貼り付けは**同じ入力欄**から段階的に選ぶ。
- Escapeと「閉じる」で閉じ、閉じたら起点の投稿へfocusを戻す。
- 入力途中で閉じても下書きは投稿IDごとに残す。

記事は中央列を読書面へ切り替えて読む。右のスレッドはその記事が添えられた元投稿の会話として残す。
保存前は「AI記事」、保存後は「Note保存済み」と表示し、Noteの開閉は既存のNote面へ渡す。

Noteの所有関係は次の一周で固定する。

- 保存前の正本はFeed投稿のProposalである。
- 保存後の編集対象はNoteであり、`accepted_from_proposal_id` で作成元を追える。
- Feedには「Note保存済み」と「Noteで読む」を出す。
- Noteを編集しても、過去のFeed投稿本文を静かに書き換えない。
- Noteを削除してもFeed投稿は残し、参照が失われたことと復元方法を表示する。

Notes側では、AIの記事から保存されたNoteに見出しの下の一行で**作成元のAI**と**自分のNotesにあること**を示し、
「元のFeed投稿を開く」で元の投稿と会話へ戻る。元Proposalが見つからない場合（Import後など）は
「AIから保存」の一般表示に留め、元投稿へ戻る導線は出さない。
この表示のためだけにNoteへ新しいauthor列を追加しない。

### 6.6 画面をまたいだ復帰

タブ、絞り込み、展開、選択中の投稿、記事、スクロール位置、返信下書きは、
TaskやNoteを開いて戻っても復元する。表示状態は正本データと分けて保持する
（`tasken:feed:view:v1`、外部AI往復の下書き、元投稿の預け先 `tasken:feed:focus-post:v1`）。

第2段階でつないだ経路:

1. 外部AIが `tasken.propose_feed_post` で短文と任意の記事草稿を送る（`payload_type: "feed_posts"`）。
2. Coreが検証し、Main Processが `ai_proposal` へ保存する。再送は同じIDへ畳む。
3. Feedは届いた投稿をそのまま読む。**読むための事前承認を挟まない。**
4. 記事の草稿は「Noteに保存」で既存の採用経路（`ApplyAiProposal`）へ渡す。NoteのIDは
   Proposal IDから決まる（`stableProposalEntityId`）ので、保存の前後で投稿・印・参照は変わらない。
5. 投稿と読者の印は再起動後も残る。

第3段階でつないだ経路（返信と質問）:

1. 人の返信は `feed_reply` Entityとして投稿のIDに保存する（`author_kind: "self"`）。
2. スレッドは選んだ投稿の右パネルへ、**古い順**に並べる（投稿列へは差し込まず、予告だけを出す）。
   返信は「学び」タブへは出さない。
3. 返信の削除はEntityの削除で、既存のトーストから元に戻せる。
4. 「AIに聞く」は `ai_requested_at` を付けて質問として残し、押した時点ではAIを起動しない。
5. 外部AIは `tasken.get_feed_context`（読み出し専用）で、未回答の質問と元の投稿の抜粋、
   直近の投稿、利用者の明示的な反応（ブックマーク・おもしろい・既知だった）を読む。
6. AIは `tasken.answer_feed_question` で返答（`feed_replies` Proposal）を送る。返答は同じスレッドへ
   並び、質問は「回答あり」になる。返答も正式データを変更せず、要対応の判断には数えない。
7. 同じ送信の再試行は同じProposalへ畳み、回答済みの質問は既定の読み出しから外れる。
8. 自分の投稿欄はFeed専用の投稿（`feed_post`）へ保存し、その保存分だけを
   「自分の記録」として読む。Notesには残さない。削除は「元に戻す」で戻せる。

### 読み物Proposalの保持とExport

- 読み物Proposalは他のProposalと同じ保存境界に置き、**自動削除しない**。将来の掃除を入れる場合も、
  投稿（`feed-post:<proposalId>`）とそこへ付いた `feed_reaction` を失わせないことを条件にする。
- 投稿は `pending` の一覧からではなく**出所のIDで追跡する**。採用後も投稿は残り、
  記事の解決先だけがProposalからNoteへ移る。
- SnapshotのExport/ImportはEntity種別の一覧（`workspaceEntityTypes`）を回すため、
  読み物Proposalは `ai_proposals.json`、読者の印は `feed_reactions.json` に含まれる。
  同じIDで戻るので、ブックマークの対応付けは保たれる。
- 「今回は見送る」は読者の状態であり、Proposalの却下や元Noteの削除とは別に扱う。
  採用したNoteを削除した場合は、本文のコピーを投稿へ残さず、草稿の本文だけを残して
  **参照先の不在**を示す（下の §5。Task参照の不在表示は未実装）。
